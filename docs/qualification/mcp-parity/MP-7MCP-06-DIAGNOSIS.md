### Reproduction (offline, scratch only)

A throwaway server reproduced the exact `tools/list`; the repository driver (`DRIVERS.antigravity`) launched agy with the committed workspace config. Result with the unchanged config on 1.5.17:

> `tool memory_search is not enabled for server mpconformance` (only `memory_fetch` is available)

The server saw `server/discover`, `initialize`, `notifications/initialized`, `tools/list` and **no** `tools/call`. The client log shows the model going through `call_mcp_tool`, not the eager `mcp_mpconformance_memory_search` tool.

Bisect (parallel runs share one schema cache directory, so the decisive results were re-run one at a time):

| Variant | memory_search cached file | Outcome |
| --- | --- | --- |
| committed catalog, all tools `eager` | 1475 B | no call, "not enabled" |
| `filters` property removed | 687 B | native eager tool, call reached the server |
| `filters` removed, long tool description added (1500 chars) | 2188 B | no call (so it is size, not the `filters` structure) |
| same catalog, **no per-tool `tools`/`eager` block** | 1475 B | call reached the server |
| all `eager` flags removed from the config but the map kept | 1475 B | call reached the server |

In the failing eager runs the client itself reported `memory_fetch` (cached file 1043 B) as the only available tool (I did not call it in an eager run); `memory_search` (1475 B) and `context_build` (1909 B) were not offered. The client therefore refuses to declare an eager tool once its description plus schema passes a size somewhere between about 1.0 KB and 1.5 KB, and the tool then reads as "not enabled". **I did not find the exact limit, and I could not test 1.5.15 (it is no longer installed)**; the claim that 1.5.15 accepted eager declarations rests on the 2026-11-24 receipt. The 1.5.16-1.5.18 changelog entries do not mention it.

Removing the whole `tools` block (lazy default) fixes it with no change to the product schema. With the fixed config the repository driver, on 1.5.18, called `memory_search`, `memory_fetch` (exact arguments, no extra fields) and `context_build` in one session.

### Root cause and confidence

Root cause: our Antigravity driver config marked all three tools `eager`; a newer Antigravity (1.5.16+, auto-updated between the version probe and the first scenario of the 2026-11-25 run) no longer declares an eager tool whose description plus input schema is above roughly 1.0-1.5 KB. `memory_search` and `context_build` exceed it, so the model never saw them as callable, the harness saw zero `tools/call`, and C2-C7 and C9 FAILED while C1 and C8 (no tool call needed) passed. **Confidence: high for the mechanism and the harness fix** (reproduced, controlled, negative control), **medium for "the update is what flipped it"** (timing and receipts, but 1.5.15 itself could not be re-run).

### Fix (harness, ours)

- `scripts/mcp-conformance/clients.mjs`: `antigravityWorkspaceConfig` no longer sets per-tool `eager`.
- `scripts/mcp-conformance/real.mjs`: `clientVersionDrift` plus a per-run `clientVersion` in the transcript. A run whose client reports two versions now records a harness failure and fails C1, instead of attributing the receipt to the probe version.
- `test/mcp-conformance-framework.test.mjs`: regression tests for both.

### Not fixed here / open

- A real `node scripts/mcp-conformance/run.mjs real antigravity` against the packaged encrypted-vault app was **NOT_RUN** (needs the packaged build and a frozen SHA, which belong to MP-PAR-02). The synthetic-server rerun above does not show C2-C9 on the real product.
- The committed Antigravity receipt still says 1.5.15 and FAIL. It is correct about the outcome and wrong about the version. MP-PAR-02 should rerun and let the new drift check decide.
- Auto-update can still change the client between runs. I found `agy update` but no verified way to pin the version; the owner should pause updates (or record the version on the card) before the MP-PAR-02 run.
- Product follow-up, optional and not done (it changes the frozen tool contract, `crates/integration-core/src/lib.rs`): `filters` is 777 of the 1282 schema bytes of `memory_search`. Shrinking it (or its repeated string-array properties) would also make eager declarations work and cut tokens for every client. The decision belongs to the contract owners, not this harness fix.

## 2. Gemini CLI 0.34.0

### What the receipts show

### Today's check (scratch, not evidence)

On 2026-11-26, with the stored login already on this machine and no login attempt of mine:

- `gemini -p "Reply with the single word OK."` in an empty directory with **no MCP server configured**: no stdout, no stderr and no exit within 75 s (stopped by the harness).
- The repository's `geminiProjectSettings` pointing at the synthetic server: the CLI **never contacted the server** (no `initialize`) and produced no output within 70 s.

So today the CLI stalls before MCP discovery and before any model turn, independent of Mind Place and of our tool schemas. In `@google/gemini-cli-core` 0.34.0 the only startup path that throws a tier error is `setupUser` / `_doSetupUser` (`code_assist/setup.js`), and the hang is consistent with that account/authentication stage, but I did not instrument it and cannot say whether it is waiting for an interactive sign-in. I did not sign in, create or enter any key.

### Schema compatibility (Gemini function declarations)

- Gemini CLI 0.34.0 forwards each MCP `inputSchema` unchanged as `parametersJsonSchema` (`tools/mcp-client.js`), then validates arguments locally with Ajv. It does not rewrite `oneOf`, `type` arrays, `format` or `exclusiveMinimum`.
- Google's structured-output page documents `anyOf`, `type: [..., "null"]`, `format` (`date-time`, `date`, `time`), `minimum`/`maximum`, `additionalProperties`, `minItems`/`maxItems`. It says `minLength`/`maxLength` are stripped without error. It does **not** mention `oneOf` or `exclusiveMinimum`. The function-calling page refers to an OpenAPI subset and warns that large or branching schemas can be rejected with 400 `INVALID_ARGUMENT`.
- Our schemas use `oneOf` (in `queries` items and in `memory_fetch.cursor`), `exclusiveMinimum` (query `weight`), `type: ["string","null"]`, `format: "date-time"`, `minLength`/`maxLength`.
- **No schema change is proposed.** Nothing in the evidence shows a schema rejection: the Gemini CLI failure precedes any model request. If the Gemini app or API later rejects a declaration, the minimal subset change is: `oneOf` to `anyOf`, drop `exclusiveMinimum` (keep `maximum`, and enforce `weight > 0` server-side, which it already does), leave the rest. That is a frozen-contract change, so it needs the contract owners and MP-PAR-01's schema-subset rules, and is not part of this PR.

### Verdict

PROVIDER_BLOCKED remains the honest cell, with the reason corrected: "the CLI does not reach a model turn on this account today (tier restriction observed on 2026-11-24; stall before MCP discovery observed on 2026-11-26)".
