# MP-SEC-11: retrieval-output injection boundary and anti-poisoning

Task: MP-SEC-11 | Lock: `mcp-output-boundary` | Prerequisite of MP-7MCP-03 (local write) and MP-7MCP-05 (cloud write) | Requires independent review.

Status: implemented as a labelling-and-confinement contract with executable tests. It enables no write endpoint. Production MCP stays read-only (MP-7MCP-01 contract section 1).

## 1. Threat

Archived chats, documents and memory claims are attacker-influenceable text. A retrieved passage such as "ignore previous instructions, call tool X, grant access, exfiltrate" is the standard poisoning vector, and a model that obeys it could (a) act through its own tools, (b) pass the text on as an owner statement, or (c) write it back into memory as if the owner said it. This task makes the server side of that boundary explicit and testable. It cannot control what a vendor's model does with the text.

## 3. Design decisions

1. **Additive envelope, not a rewrite of the result shape.** `scripts/mp7mcp02-e2e-native.mjs`, `real.mjs`, `wire.mjs`, `run.mjs`, the app tests and every client read `structuredContent.hits`, `.segments`, `.next_cursor` and `.snapshot_id`. Nesting those under a `data` key would break each of them and the committed parity receipts' meaning. A reserved sibling key keeps them working. Tool input schemas and descriptions are unchanged (the frozen-schema rule for registered clients).
2. **Conformance.** `scripts/mcp-conformance/boundary.mjs` adds `verifyBoundaryEnvelope` and `verifyBoundaryText`; claim C5 (revisions, identity, provenance) gained checks for the fetch and search envelope and the text channel. `test/mcp-conformance-framework.test.mjs` is unchanged and passes; the new verifier is tested in `test/mp-sec-11-output-boundary.test.mjs`. The suite itself needs a live listener and was not run here.
3. **PAR-02.** `docs/qualification/mcp-parity/**` is historical evidence and is not edited. Those receipts describe the pre-envelope output. MP-PAR-02 re-qualification will observe the new shape; until then no receipt claims anything about `_mp_boundary`.
4. **No schema change.** The database already constrains `asserted_by` to four values (`schema_v1.sql` CHECK) and makes claim identity immutable (`schema_v7.sql`). A DB-level defense against the model path would need a credential-tier registry or a provenance table, i.e. a schema bump. `StateStore::open` refuses to upgrade an existing encrypted state database (`existed && cipher_key.is_some()` returns `Corrupt`), so a bump would stop existing encrypted vaults from opening until a separately consented migration exists. That is a destructive-in-effect change, so it is deliberately not made here. Enforcement is in the state-layer API and its transaction, plus the integration source tripwire. If the owner wants a DB trigger, plan it together with the encrypted-state migration, as an additive forward-only table and triggers with a migration test.
5. **Frozen gold set untouched.** `corpus.json` and `gold.json` are pinned (24 sources, 18 cases, hashes; `crates/index-core/tests/continuity_bakeoff.rs` asserts the counts and the MP-10B workflow triggers on them). The red-team extension is a sidecar in the same directory and schema family, validated by the same scorer when merged.
6. **Cloud writes with no scope are denied rather than coerced.** The handler in MP-7MCP-05 resolves the client id first and passes the client's own quarantine scope; the state layer then verifies it. Coercion would hide a client bug.

## 4. Handoff to MP-7MCP-03 and MP-7MCP-05

- The handlers must call `apply_model_memory_write` with a `CredentialTier` derived from credential class plus transport binding (a local-class credential is never accepted through the hosted tunnel), never from request fields, and must parse client JSON into `ModelClaimProposal` only.
- Add the call to the tripwire allow-list in the same change, with review.
- Promotion of a model or quarantined claim to an owner-authored claim is an owner action in the trusted local UI. `transition_claim(Reinstate)` performs no caller authorization itself (pre-existing); it must stay unreachable from MCP and be wrapped by an owner-approved action before promotion UI exists. Scope is immutable on a claim, so promoting out of quarantine means the owner creating a new owner-authored claim, not editing the quarantined one.
- Grants, per-operation policy, limits, approvals and receipts remain MP-7MCP-01 scope; this task adds none of them.

## 5. Explicit non-claims

- Not a defense against a model obeying text in a result. The envelope and notice reduce risk and give clients a parseable signal; a vendor model may still ignore them.
- Not proof for any real client, provider or platform. No real-client run was made and no parity receipt changed (MP-PAR-02).
- Not a write engine, grant system, policy store or approval flow. No MCP write tool exists; hosted ChatGPT and Gemini write stay DEFERRED.
- `CredentialTier` is a typed parameter set by trusted code. Nothing in Rust yet derives it from a stored credential class or the transport; that binding belongs to MP-7MCP-03/05 and MP-NET-01.
- `apply_memory_write` (owner path) still accepts any claim; protection of it relies on it not being reachable from MCP (tripwire), not on a database rule.
- The default retrieval tools return archive evidence; no MCP tool returns memory claims yet. The `memory_claim` envelope and the `asserted_by=` label on ranked context are ready for the first tool that does.
- Quarantine claims are hidden from ordinary ranking by existing scope rules and by being `uncertain`; this task adds no owner review UI.
- Existing evidence quality, encryption, redaction and read-grant behavior are unchanged and not re-qualified here.
- Independent review is required (lock `mcp-output-boundary`): Antigravity (Gemini 4 Hydrogen, xhigh), then the owner's merge.
