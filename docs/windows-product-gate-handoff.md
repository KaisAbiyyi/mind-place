# MP-CI-WIN-01: Windows product gate investigation

**Status: BLOCKED.** This branch adds an experimental input fingerprint and
its tests. It does not optimize scheduling or provide a Windows acceptance
check. The existing native job is unchanged and Draft feedback is not native
qualification. This is not an attestation and must not be used to skip tests.

The fingerprint hashes sorted Git tree entries (path, mode and Git object ID)
from an immutable tested commit. Only ordinary Markdown files in `docs/` are
excluded. This exclusion is provisional: before using it for scheduling, an
independent review must establish that no build, test, packaging, dynamic file
scan or future workflow consumes those files. Any input policy must bind its
own version and the full Windows execution semantics. The merge commit, not
just the PR head, is needed to account for changes in the base branch.

## Trust boundary requiring resolution

The `pull_request` workflow, its verifier and its named steps come from the PR
merge tree. An adversarial PR can modify them, produce a successful job or step
with the expected name, and change its own acceptance decision. GitHub's run
and step metadata are useful evidence that those names succeeded, but do not
independently prove that the intended commands ran. Merely hashing the same
PR-controlled workflow, or trusting a receipt generated by it, does not solve
this. A same-name status check also cannot by itself establish that an
untrusted PR could not replace its implementation.

A deployable design needs an independently enforced trusted verifier and
execution policy, such as an organization-enforced required workflow pinned to
reviewed policy, with the actual repository capabilities and enforcement
verified. It must execute untrusted PR code without privileged credentials,
validate GitHub-owned run/attempt/job/step data against the trusted policy,
reconstruct the tested merge tree and independently compare the current tree,
and reject absent or ambiguous proof. Its concurrency mechanism must recheck
proof after obtaining a per-PR slot, account for superseded heads and GitHub's
pending-job replacement behavior, and never accept a skipped native job.
Repository-level enforcement is outside the authorization for this task.
Whether a suitable required-workflow facility is available has not been verified.

At investigation time `main` was unprotected and the repository had no active
rulesets. Before merge enforcement, configure branch protection or rulesets to
require the stable trusted Windows acceptance check and the existing fast,
security, storage and 100K checks after verifying their actual names and event
behavior. Branch protection must also prevent untrusted changes from replacing
the policy that creates the required check. Do not interpret this as an exact
ready-to-apply check list: no trustworthy Windows acceptance check exists yet.

No native proof has been minted or reused by this branch. A later implementation
must cover all negative and concurrency cases in the assignment and validate
real GitHub run attempts before claiming a performance improvement.
